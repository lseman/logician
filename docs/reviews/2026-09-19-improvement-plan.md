## 3. P1 — medium (each ~1 week or less)

1. **Fix prompt-cache invalidation** (biggest $/latency lever on hosted endpoints): memoriam **prepends** a memory system message at position 0 every turn (busts the whole prefix cache); legroom rewrites the entire payload through Python every provider call (and every retry). Fixes: inject memory in the stable system-prompt dynamic tail refreshed only on memory-revision change; prefix-memoize legroom (history is append-only — compress only the new tail, splice); emit `cache_control` breakpoints where the endpoint supports them. Upstream is actively investing here (#12431, #12332) — worth matching their approach. **Done 2026-09-20 (all three):** (a) the append-only prefix property is pinned at wire level by tests (`__tests__/infrastructure/prefix-stability.test.ts`) and the loop reports per-request divergence — `context_update` carries `prefixStable`/`prefixDivergedAt`/`prefixRewritten`, counted as `prefixDivergences` in `summarizeTrajectory`; (b) memoriam was found already fixed in HEAD — trailing system append (never touches the prefix; `normalizeProviderMessages` re-roles it at the transport boundary) + revision-keyed retrieval cache so the injected block stays byte-stable until the store mutates (`prompt-cache-stability.test.ts`); legroom likewise already carries a per-message FNV-1a prefix memo with retry fast-path and tail-splice aligned to `protect_recent`, disabled under semantic-dedup (cross-message phases); (c) `streamOptions.cacheRetention` — previously dead at the last hop — is now forwarded into the OpenAI wire as `prompt_cache_retention` (provider-adapter + backend, provider validates values); explicit Anthropic `cache_control` breakpoints remain under P2 provider-wire-breadth (needs the Anthropic `/v1/messages` wire, not this OpenAI-compatible harness).
2. **Async batched session journal** — `session-store.ts:729-764` does ~3 sync fsyncs + 3 open/close pairs per persisted message, on the event loop; a 20-tool-call turn ≈ 120 fsyncs blocking streaming/TUI/hooks. One open, buffered appends, coalesced fsyncs at turn end/timer, async meta, drop the per-append dir fsync. **Done 2026-09-20:** the fsync/meta coalescing (100 ms window + 512 KiB byte threshold) was already at HEAD; the remaining per-entry cost is gone — the journal keeps one append handle per flush burst instead of open/write/close + `mkdirSync` per entry (1 write syscall per message), `flush()` fsyncs through the open handle and releases it so a file deleted or replaced between bursts is picked up by the next append (writes through an fd to an unlinked inode succeed silently, so per-entry revalidation was the old code's only protection — burst-boundary revalidation keeps it at ~100 ms granularity), ENOENT retry rebuilds a removed session dir, and `close()` flushes + releases. Regression tests pin append-after-truncate (inode swap), append-after-dir-removal, and close-flush; both fail under a hold-the-fd mutation.
3. **Persistent graphician worker** — `graphician.ts` spawns a fresh Python process per query (re-imports stack, opens the 571 MB DB, 1–10 s) and can stall a tool slot 5–60 s on rebuild-on-query. Reuse the `JsonlWorker` pattern with a background debounced incremental rebuild decoupled from query latency. **Done 2026-09-20:** `graphician worker` subcommand runs a persistent JSONL server (`interfaces/transport/jsonl_worker.py`, same contract as legroom's `sdk_worker`): `query` answers in-process against a fingerprint-keyed process-lifetime graph cache (the existing `tool_response_cached` path — DB/WAL mtime+size fingerprint reloads the graph automatically after a refresh), while `refresh` spawns the smart `graphician build` in a **child process** reaped by a daemon thread, so a query never blocks on a rebuild (at most one refresh at a time; the TS side fires it and moves on). The tool keeps the per-call CLI spawn as a fallback (worker failures get a 60 s cooldown and fall through to the old blocking-refresh path, which the shared 5 s cooldown gate keeps from double-building). Verified: warm status query 660 ms → 12–33 ms, search with params 159 ms; Python `tests/test_jsonl_worker.py` pins in-process serving, non-blocking refresh + graph reload, dedupe, and protocol-error survival; TS `graphician-worker.test.ts` pins the wire contract.
4. **Predictive compaction** — while a turn streams, project token growth from `usage` and pre-compact the tail (or pre-render snapcompact frames) in the background, so `context_full` mid-loop doesn't stall on a synchronous LLM summary.
5. **Wire memoriam auto-observation** (batched async `afterToolCall`/`message_end` → `observe`) or drop the doc claim — today memories are only written when the model calls `retain`; recall quality degrades silently. Plus a shared read-only tool cache across the subagent spawn tree (subagents re-execute identical read-only work today).

## 5. Inspiration-repo ideas

- **headroom** (context compression layer, 55.9k → 24.3k tokens, 60–95% savings, important lines preserved byte-for-byte): its killer idea is **CCR — Compress-Cache-Retrieve**: compress tool outputs losslessly, keep originals in a store, let the model retrieve the original on demand. Logician's legroom is lossy pre-provider compression; a reversible CCR mode (or a legroom upgrade to headroom's pipeline: per-content-type compressors + statistical JSON/array compression 70–90% + AST code compression) is the clearest cross-repo win.
- **deepseek-harness**: everything-is-a-plugin architecture; its benchmark harness (logician analog: `log-eval`) is worth a look for eval methodology, not for porting.
- **claude-mem / agentmemory**: persistent-memory patterns overlap with memoriam; nothing to port beyond confirming memoriam's direction.
- **gsd-core**: logician already integrates GSD for planning (`.planning/`); no action.

## 8. P3 — harness / loop / configuration deep-dive (2026-09-20)

Fresh audit of the loop, harness, and config surfaces (post-P1). The loop is mature (event-replayed, budgeted, parallel tool batches with sequential barriers, steering/continuation queues, acceptance contracts, loop guards); the highest-value gaps are where **runtime state and config don't track each other**, and in the config surface's maintainability.

1. **Per-model capability caps** (harness/loop × config): `AgentModelConfig` is only `{ name, model, url }` (`config.ts:139–171`), while the compaction trigger reads a **global** `contextWindowTokens` closure — `deps.contextWindowTokens()` → `() => config.contextWindowTokens` (`builtin-hooks.ts:268`, wired at `extension-runtime.ts:160`, `agent-session.ts:1112`). Model cycling (Ctrl+L, `ModelSelector.selectOption` sets only model+url) therefore keeps the old window: cycling to a small local model → `context_full`/forced compaction mid-run; cycling to a 1M-window model → premature compaction wasting tokens. Fix: optional `contextWindow` / `maxTokens` / `supportsThinking` on each `models[]` entry; an `effectiveContextWindow(activeModel)` resolver (per-model ?? global) feeding the compaction deps, the `context_update` emission, and the token budget; the selector UI shows the window per option. **S–M, high** — core-loop correctness.
2. **Declarative env-override layer** (config): 21 scattered `process.env.LOGICIAN_*` reads; the env→bridge mapping is hand-wired per field in `runtime-config.ts:99–179` (and `LOGICIAN_CONTEXT_WINDOW`/`LOGICIAN_CTX_SIZE` duplicate). One `ENV_OVERRIDES: Readonly<Record<configKey, envVar>>` table (keys derived from the settings registry, so it can't drift), applied as an explicit resolution step: defaults < global < project < env. Non-config env (`LOGICIAN_CONFIG`, `LOGICIAN_TRUST`, debug flags) stays ad hoc. **S, med-high** — makes every key overridable in CI/containers; precedence becomes testable and documented.
3. **Text-stagnation: nudge, then abort** (loop): a `TextLoopDetector` hit ends the run `blocked` immediately (`agent-harness.ts:423–440`); the intervention records `action: "change_strategy"` but nothing acts on it. First hit → inject one bounded strategy-change nudge (mirror the soft-tool-manager escalation pattern; say what repeated); second hit → block as today. **S, med** — rescues stuck runs the same way verification-repair already does.
4. **Schema-driven config validation** (config): `validateConfig` is ~700 lines of hand-coded per-field checks (`config.ts:93–789`) duplicating the `SETTINGS_SCHEMA` registry that already carries type/min/max/enum/defaults (built for the settings UI). Derive type/range/enum/unknown-key checks from the registry; keep only genuinely cross-field rules by hand (`models[]` entry shape, URL fields). Cuts the validator ~60–70 % and makes "new key silently unvalidated" structurally impossible. **M, med.**
5. **Resolved-config diagnostics** (config): doctor reports config validity and the active model but not *where each value came from*. `resolveRuntimeConfig` already loads global/project separately — emit a precedence table (key → value → layer) from a `config show` / doctor flag. **S, med** — first thing to want when behavior is surprising.
6. **Config profiles** (config): no named preset bundles; switching between e.g. "cheap local model, relaxed guards" and "strong model, strict verification" means editing the file. `profiles: Record<string, Partial<LogicianTuiConfig>>` + `/profile <name>` through the existing `AgentSession.configure(patch)` runtime path. Pairs with item 1 (a profile can carry per-model caps). **M, med.**
7. **Harness turn-phase decomposition** (harness, do last): `runAgentLoopInternal` is 811 lines mixing ~10 concerns (budget, steering, soft tools, context transform, provider call, response processing, loop detection, tool batch, permission escalation, context budget/compaction, config refresh, stop policies, acceptance). Extract per-turn phases over a shared `TurnContext` record; the P0 event-replay infrastructure is the safety net — pin event-stream equivalence for representative sessions before/after. **M–L, med** — maintainability, not behavior.

**Status (2026-09-20):** items 1–5 and 7 are done.
- **Item 1 (per-model caps):** `AgentModelConfig` now carries optional `contextWindow` / `maxTokens`; `resolveModelContextWindow` / `resolveModelMaxTokens` (`harness/live/model.ts`) resolve per-model ?? global and are used at all four consumption points (provider options, compaction engine wiring, per-iteration `context_update` + forced compaction, session snapshot). The model selector shows the cap per option (`… · 32k ctx`). Config validation drops invalid caps with a per-entry warning. Tests: resolver fallback matrix, `context_update` reports the active model's window. (`supportsThinking` intentionally not added — no consumer.)
- **Item 2 (env layer):** declarative `ENV_OVERRIDES` table in `runtime/configuration/env-overrides.ts` (model, baseUrl, systemPrompt, reasoner, contextWindowTokens [incl. legacy `LOGICIAN_CTX_SIZE`], hooks, theme, postEditDiagnostics), type-coerced against the settings registry with load-time drift check, applied as the explicit `defaults < global < project < env` step in `resolveRuntimeConfig`. All hand-wired `process.env.LOGICIAN_*` reads for those keys removed (config factory, theme init, agent bridge, doctor). Uncoercible values warn and leave the config value standing.
- **Item 3 (stagnation nudge):** first `TextLoopDetector` hit on a text-only response injects one bounded strategy-change nudge (`[stagnation-nudge]`, detector reset, run continues); a second hit blocks as before. A first hit while tool calls are landing is counted only (the run is making work progress) — the batch runs and the next text hit blocks. All three paths emit `harness_intervention` events.
- **Item 4 (schema-driven validation):** `validateConfig` is now registry-driven — flat scalar keys (string/url/number/boolean/enum) validate from their `SETTINGS_SCHEMA` spec in one loop, and sub-objects (`lsp`, `legroom`, `memoriam`, `compaction`, `truncation`, `tools`, `webSearch`, `permissions`) go through a shared `validateSubObject` (unknown-key warnings + registry fields, recursing into `truncation.microCompactMaxChars`). Hand-written blocks survive only for what the registry can't express: `models[]` shape, temperature clamping, reasoner registry, cwd fs check, `allowedPaths`, and string-array/object element filtering. Validator body 719 → 229 lines (−68 %). Four soft knobs (`contextWindow`, `contextWindowTokens`, `compaction.reserveTokens`, `compaction.keepRecentTokens`) carry `silent: true` in the schema — range violations drop without a warning (legacy alias / "0 means unset"). All 53 config tests pass; one pinned message updated (maxResults range text unified to the generic form).
- **Item 5 (resolved-config diagnostics):** `resolveRuntimeConfig` returns a `provenance` table (key → value → layer, layer ∈ global/project/env) built from the RAW layer inputs — the parsed files plus the applied env overrides — so injected defaults never appear and shadowed values never surface. Loaders keep the parsed raw object (`ResolvedLogicianConfig.raw`); `applyEnvOverrides` reports the keys it applied. Doctor renders the table in the Configuration section (text and `--json`); nested sections attribute at field level (`lsp.timeoutMs [project]` over `lsp.enabled [global]`), passthrough objects and arrays report at their top-level key.
- **Item 7 (turn-phase decomposition):** `runAgentLoopInternal` (919 lines) split into `agent-harness.ts` (run setup + loop skeleton + public contract, ~220 lines) and `turn-phases.ts`: ten inner-loop phases (`checkBudget`, `beginTurn`, `applySoftToolRequirements`, `requestProviderTurn`, `processAssistantResponse`, `executeToolCalls`, `enforceSoftToolCompliance`, `checkPermissionEscalation`, `manageContextBudget`, `endTurn`, `prepareNextTurn`, `decideTurnContinuation`) over a shared `TurnContext` record, run as a declarative `INNER_PHASES` sequence by `runPhaseSequence`. The post-turn stop-policy → acceptance-repair flow is deliberately sequential, not a phase sequence: a `break` from the stop policies falls through to the acceptance phase, a `continue` from either re-enters the outer loop, and only the acceptance phase's `break` exits the outer loop. **Equivalence, not just tests:** a golden test (`agent-loop-golden.test.ts`) event-records the loop through a fake backend on four representative sessions (text-only finish, tool batch + budget cap, steering + permission escalation, maxIterations stop) and asserts the normalized event stream — `seq`/`ts` stripped — is byte-identical to the pre-refactor harness; all 86 pre-existing agent tests (steering, permissions, inference mode, compaction, stop policies, acceptance repair, budgets) pass unchanged.
